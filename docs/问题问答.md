## 一、严重问题

### Q1：问数聊天中点击"新对话"按钮会怎样？

**A：返回 404，功能完全不可用。**

- 前端 `components/ask-number-chat.tsx` 第 2232 行调用：
  ```
  POST /api/chatdb/chats/sessions/${sessionId}/reset
  ```
- Next.js 路由目录 `app/api/chatdb/chats/sessions/` 下只有 `route.ts`（处理会话创建），**不存在** `[sessionId]/reset/route.ts`
- QA 重置路由存在于 `app/api/chatdb/qa/sessions/[sessionId]/reset/route.ts`，但 chat 的对应路由缺失
- 后端接口 `POST /api/v1/chats/sessions/{sessionId}/reset` 已实现，只是前端没有对应的代理路由

**修复方案**：新增 `app/api/chatdb/chats/sessions/[sessionId]/reset/route.ts`，将请求代理到后端 `/api/v1/chats/sessions/${sessionId}/reset`。

### Q2：SSE 流结束时前后端行为一致吗？

**A：不一致，终止标记不匹配。**

| 对比项 | 后端（Go） | 前端（sse.ts） |
|--------|-----------|---------------|
| 终止方式 | 发送 `data: {"event":"end",...}` 后关闭连接 | 期待 `data: [DONE]` 作为终止标记 |
| `[DONE]` | 后端**从不发送** | 前端遇到 `[DONE]` 会跳过该行 |

- 后端发送 `{"event":"end"}` 消息后关闭 `respChan`，控制器退出读取循环
- 前端 `readSSEStream()` 遇到 `[DONE]` 会 `continue` 跳过，但后端根本不发送它
- 实际上前端靠 `reader.read()` 返回 `done: true` 来结束循环，功能勉强可用
- 但后端的 `{"event":"end"}` 帧会被前端当作普通帧处理，而非终止信号

**影响**：
1. 前端无法可靠判断流何时真正结束
2. 如果需要在 `end` 事件时做清理操作（如关闭 loading 状态），逻辑可能不可靠

**修复方案**：统一终止协议，建议后端在 `end` 事件后额外发送 `data: [DONE]`，或前端在解析到 `event: "end"` 时主动终止读取循环。

### Q3：长对话场景下 SSE 连接会断开吗？

**A：很可能断开，心跳机制失效。**

| 对比项 | 后端（Go） | 前端（sse.ts） |
|--------|-----------|---------------|
| 心跳格式 | `event: ping\n\n`（标准 SSE） | 只解析 `data:` 开头的行 |
| 实际行为 | 定期发送心跳包 | 心跳被完全忽略 |

- 后端通过 goroutine 定期推送 `event: ping\n\n` 作为 SSE keep-alive
- 前端 `readSSEStream()` 的行解析逻辑为：`if (!trimmed.startsWith('data:')) continue`
- `event:` 开头的行被直接丢弃，心跳永远到不了前端

**影响**：
- 长时间生成的 AI 回复期间，中间代理（Nginx/CDN）或浏览器可能因空闲超时断开连接
- 用户看到的现象：回答在生成途中突然中断，无 error 事件

**修复方案**：前端 `readSSEStream()` 增加 `event:` 行的解析支持，至少识别 `ping` 事件以维持连接活跃状态。

## 二、中等问题

### Q4：后端已有接口但前端没有代理路由的有哪些？

**A：以下 8 个后端接口在前端完全无法访问。**

| 后端端点 | 方法 | 功能 | 前端路由状态 |
|---------|------|------|-------------|
| `/api/v1/config/db/setConfig` | POST | 新增数据库配置 | 无 |
| `/api/v1/config/db/updateConfig` | PUT | 更新数据库配置 | 无 |
| `/api/v1/config/db/deleteConfig` | DELETE | 删除数据库配置 | 无 |
| `/api/v1/config/db/listConfig` | GET | 获取数据库配置列表 | 无 |
| `/api/v1/config/ai/model/list` | GET | 获取 AI 模型列表 | 无 |
| `/api/v1/export/download` | GET | 导出文件下载 | 无 |
| `/api/v1/user/register` | POST | 用户注册 | 无 |
| `/api/v1/popular-questions` | GET | 用户维度热门问题 | 无（QA 版有） |

**说明**：
- 数据库配置相关 4 个接口全部缺失，若前端有"数据库管理"功能则完全不可用
- AI 模型列表接口缺失，前端可能硬编码了模型选项
- 导出下载接口缺失，用户无法导出聊天/分析结果
- 用户注册接口缺失，新用户无法自助注册
- `popular-questions` 有 QA 版（`/api/v1/qa/popular-questions`），但用户维度的版本（`/api/v1/popular-questions`）缺失

**修复方案**：按需新增 Next.js 代理路由，或在已有 catch-all 路由中纳入这些路径。

### Q5：Admin Login 的实现有什么问题？

**A：两个问题——未使用统一请求工具、token 过期时间不一致。**

**问题 1：未使用 `chatDbFetch`**

- `app/api/chatdb/admin/login/route.ts` 手动拼接 URL 并使用原生 `fetch`
- 其他所有代理路由均使用 `chatDbFetch()` 统一处理
- 该路由无法受益于统一的错误处理逻辑

**问题 2：Cookie 过期时间与 JWT 不一致**

| 对比项 | 后端 JWT | 前端 Cookie |
|--------|---------|------------|
| Admin token 有效期 | **8 小时** | **7 天** |
| User token 有效期 | **24 小时** | 由登录响应设置 |

- 前端登录成功后设置 `chatdb_admin_token` cookie，过期时间固定 7 天
- 后端 Admin JWT 只有 8 小时有效期
- **后果**：8 小时后 JWT 已失效，但 cookie 仍在，前端会持续发送已过期的 token，后端返回 401，用户需要重新登录

**修复方案**：
1. Admin login 路由改用 `chatDbFetch`（需支持无 token 调用）
2. Cookie 过期时间与后端 JWT 保持一致，或根据登录响应中的 `expire` 字段动态设置

## 三、低风险问题

### Q6：Token 自动登录有什么性能隐患？

**A：每次无 token 请求都会触发一次登录。**

- `chatDbFetch` → `getChatDbToken` 的逻辑：若无 cookie token、无 Authorization header、无环境变量 `CHATDB_JWT_TOKEN`，则用 `CHATDB_USERNAME`/`CHATDB_PASSWORD` 调用登录接口
- 每次请求独立执行此流程，**登录结果不缓存**
- 高并发场景下（如页面加载时发起多个并行请求），会同时发起多次登录

**影响**：
- 不必要的后端负载（大量重复登录请求）
- 可能触发后端登录频率限制
- 响应延迟增加（每个请求多一次网络往返）

**修复方案**：在模块级别缓存 token 和过期时间，仅在 token 过期时重新登录。

---

### Q7：前后端字段映射有什么隐式约定？

**A：请求体字段名不一致，依赖环境变量硬编码默认值。**

| 前端字段 | 后端字段 | 前端默认值 | 来源 |
|---------|---------|-----------|------|
| `context` | `history` | `[]` | 字段名不同 |
| — | `ai` | `'deepseek'` | `CHATDB_AI` 环境变量 |
| — | `model` | `'deepseek-chat'` | `CHATDB_MODEL` 环境变量 |
| `databaseId` | `databaseId` | `1` | `CHATDB_DATABASE_ID` 环境变量 |

**风险**：
- `context` → `history` 的映射是隐式的，如果有人直接参考后端 API 文档调用前端，会用错字段名
- `ai`、`model`、`databaseId` 的默认值硬编码在前端代理层，后端更改模型名称或数据库 ID 分配策略后，前端会静默失败
- 这些默认值对前端开发者不可见（隐藏在代理路由的 body 转换中），调试困难

**修复方案**：
1. 在前端 SDK/API 层明确文档化字段映射关系
2. 考虑让后端也接受 `context` 作为 `history` 的别名，或前端统一使用 `history`

---

### Q8：CORS 配置是否安全？

**A：当前配置允许所有来源，生产环境应限制。**

- 后端使用 GoFrame 内置的 `ghttp.MiddlewareCORS`，默认允许所有 Origin
- 由于前端通过 Next.js BFF 代理层访问后端，浏览器实际不会跨域直接调后端
- 但如果将来有需求让浏览器直接调后端 API，当前的全开放 CORS 会成为安全隐患

**修复方案**：生产环境中配置 CORS 允许的 Origin 白名单，或确保所有前端请求都通过 Next.js 代理。
