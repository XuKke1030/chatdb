### 1.1 技术栈

| 层   | 技术                                     |
|------|------------------------------------------|
| 语言 | Go 1.25                                  |
| 后端 | GoFrame v2（`api → controller → service → logic → dao → model` 分层） |

```

  └─ 慢问路径（slow path）：LLM 生成 SQL → isReadOnlySQL 校验 → 执行 → Markdown 表格 → 流式输出
```

## 三、P0 — 必须立即修复

### 3.1 Shell 命令执行 MCP 工具：黑名单可绕过

**文件**: `internal/logic/mcp/mcp_tool_shell.go:49`

**问题**: LLM Agent 可通过 `RunSafeShellCommand` MCP 工具执行任意 shell 命令。黑名单验证存在多处绕过路径：

| 绕过方式 | 原理 |
|----------|------|
| 登录 shell 执行 | `/bin/zsh -lc` 会 source `.zshrc`/`.zprofile`，预定义函数或别名可绕过首 token 检查 |
| `eval` 未禁用 | `echo eval $(base64 -d cmd)` 首 token 是合法的 `echo` |
| `$( ` 被禁但反引号单独处理不完整 | 黑名单逐字匹配可能遗漏 Unicode 空格或编码变体 |
| `cwd` 无路径校验 | LLM 可设置 `cwd=/etc` 或任意敏感目录 |
| Windows 不可用 | 硬编码 `/bin/zsh` 在 Windows 上直接 crash |

**代码片段**:
```go
// 第 49 行：登录 shell 执行
cmd := exec.CommandContext(ctxTimeout, "/bin/zsh", "-lc", command)
if cwd != "" {
    cmd.Dir = cwd  // 第 51 行：cwd 无校验
}
```

**建议**:
- 移除此 MCP 工具，或改用严格白名单模式（仅允许明确列出的命令和参数模式）
- 用 `exec.Command` 直接执行二进制而非通过 shell，避免 shell 解析
- 如需保留，增加 `cwd` 路径白名单校验、移除登录 shell（`-l` 标志）、添加 build tag 限制平台

### 3.3 JWT 开发绕过随生产二进制发布

**文件**: `internal/logic/middleware/jwtAuth.go:16`

**问题**:

```go
var jwtDevBypass = strings.EqualFold(os.Getenv("CHATDB_JWT_DEV_BYPASS"), "true")
```

此标志不是编译开关，随生产二进制发布。若生产环境误设此环境变量（容器配置错误等），所有鉴权静默失效——请求以 `userId=0` 放行而非拒绝。

同时，Admin JWT secret **无环境变量覆盖**（`consts.go` 仅覆盖 user subject 的 `CHATDB_JWT_SECRET`），管理后台可用硬编码的 `chatdb-admin-jwt-secret-key-2024` 生成合法 token。

**代码片段**（`consts.go:236-257`）:
```go
// 仅覆盖 user subject
if envSecret := os.Getenv("CHATDB_JWT_SECRET"); envSecret != "" {
    Config.Jwts[0].Secret = envSecret
}
// 无 CHATDB_ADMIN_JWT_SECRET 覆盖
```

**建议**:
1. 使用 Go build tag（`//go:build dev`）替代环境变量控制绕过，确保生产编译不含此代码
2. 在 `consts.go` 中增加 `CHATDB_ADMIN_JWT_SECRET` 环境变量覆盖
3. 替换 `config.yaml` 中的弱默认 secret（至少 32 字节随机）

### 3.4 无任何速率限制

**文件**: `internal/cmd/cmd.go:96`

**问题**: 路由组仅配置 `RequestMetrics` 和 `HandlerResponse` 中间件，无 per-IP / per-user 限流。

| 风险接口 | 影响 |
|----------|------|
| `/api/v1/chats` | 每次请求触发 LLM API 调用（有成本），无限制可被刷爆 API 额度 |
| `/api/v1/admin/login` | 无暴力破解防护，可无限尝试密码 |
| `/api/v1/user/login` | 同上 |
| `/api/v1/user/register` | 可批量注册垃圾账号 |

**建议**:
- 使用 GoFrame 限流中间件或 `golang.org/x/time/rate`
- Chat 接口：至少 10 req/min/user
- 登录接口：至少 5 req/min/IP，连续失败 5 次锁定 15 分钟
- 注册接口：至少 3 req/min/IP

## 四、P1 — 高优先级

### 4.1 SSE 通道双重关闭将导致 panic

**文件**: `internal/logic/ai/chat.go:43-48, 192`，`internal/logic/ai/chan_out.go:53`

**问题**: `respChan` 存在三条关闭路径，可能重叠：

```go
// chat.go:43-48 — defer 关闭
defer func() {
    if err != nil {
        respChan <- err
        close(respChan)  // 路径 1
    }
}()

// chat.go:192 — 超时分支关闭
if timeoutCtx.Err() == context.DeadlineExceeded {
    close(respChan)  // 路径 2
}

// chan_out.go:53 — goroutine defer 关闭
defer close(respChan)  // 路径 3
```

场景：Agent.Stream 超时 → 父函数路径 2 close → 但 goroutine 的 defer 路径 3 也会 close → **panic: close of closed channel**。

**建议**: 使用 `sync.Once` 包装 close 操作，或统一由 `AiChatStreamOut` goroutine 负责关闭，父函数不主动 close。

---

### 4.2 LLM 生成 SQL 的只读检查可绕过

**文件**: `internal/logic/mcp/mcp_tool_db.go:305-356`

**问题**: `isReadOnlySQL` 基于关键字黑名单，存在以下绕过路径：

| 绕过方式 | 示例 | 原因 |
|----------|------|------|
| `SHOW CREATE TABLE` | `SHOW CREATE TABLE users` | 泄露完整 schema（含列类型、约束） |
| `mysql` 系统库 | `SELECT * FROM mysql.user` | 暴露数据库用户凭证 |
| `HANDLER` 语句 | `HANDLER users OPEN; HANDLER users READ FIRST` | 不以 SELECT/WITH 开头，绕过前缀检查 |
| 无结果限制 | `SELECT * FROM huge_table` | 全量物化到内存，OOM 风险 |
| `LOAD DATA` | `LOAD DATA INFILE '/etc/passwd'` | 未在黑名单中 |

**代码片段**:
```go
// 第 335-341 行：只检查前缀
if strings.HasPrefix(sql, "SELECT") || strings.HasPrefix(sql, "WITH") {
    return true
}
if strings.HasPrefix(sql, "SHOW") {
    return true  // SHOW CREATE TABLE 被允许
}
```

**建议**:
1. 添加 `LIMIT` 注入：如果 SQL 无 LIMIT 则自动追加 `LIMIT 1000`
2. 在执行层使用只读事务：`SET SESSION TRANSACTION READ ONLY`
3. 禁止访问 `mysql`、`information_schema`、`performance_schema` 系统库
4. 禁止 `HANDLER`、`LOAD DATA` 语句

### 4.3 数据库错误信息直接透传给用户

**文件**: `internal/logic/mcp/mcp_tool_db.go:63`，`internal/logic/ai/chan_out.go:43`

**问题**:

```go
// mcp_tool_db.go:63
outStr := fmt.Sprintf("数据库执行失败：%s", queryErr.Error())

// chan_out.go:43
Data: g.Map{"message": err.Error()},
```

数据库错误通常包含表名、列名、连接信息。Controller 层 `askNumberBusinessError`（`ai_chat_v1_chats.go:220`）仅过滤含 "sql"/"database"/"数据库" 的错误，其他内部错误（网络超时、栈追踪等）直达用户。

**建议**:
- 生产环境只返回通用错误消息（如"查询执行失败，请稍后重试"）
- 详细错误仅写入服务端日志
- 对 `sendStreamError` 返回内容做白名单映射，而非黑名单过滤

---

### 4.4 getSizeQuery SQL 注入

**文件**: `internal/logic/mcp/mcp_tool_db.go:296-298`

**问题**:

```go
fmt.Sprintf(
    "SELECT ROUND(SUM(data_length + index_length) / 1024 / 1024, 2) AS 'Size (MB)' FROM information_schema.tables WHERE table_schema = '%s'",
    dbname,
)
```

`dbname` 从 DSN 解析而来。若 DSN 被篡改（如 `db'; DROP TABLE t--`），可注入 SQL。虽然 DSN 由管理员配置，但违反纵深防御原则。

**建议**: 改用参数化查询 `WHERE table_schema = ?`。

## 五、P2 — 中等优先级

### 5.1 无 Token 吊销机制

**问题**: 禁用用户或修改权限后，已签发 JWT 仍有效至自然过期（用户 24h，管理员 8h）。被禁用用户可继续访问。

**建议**:
- 实现 token blocklist（Redis SET + TTL = token 剩余有效期）
- 或在 JWT claim 中嵌入 `permVersion`，鉴权时比对当前版本

---

### 5.2 用户消息和 SQL 全量审计日志

**文件**: `ai_chat_v1_chats.go:125`，`mcp_tool_db.go:65`

**问题**: 用户问题和 LLM 生成的 SQL 以 Info 级别持久写入日志。涉及人事、案件、调查等敏感内容的查询存在合规风险。

**建议**:
- 敏感内容日志级别降为 Debug（生产默认关闭）
- 或对日志中用户输入做脱敏处理

---

### 5.3 DB 连接池未配置

**文件**: `config/config.yaml:92-94`

**问题**: GoFrame 默认 MaxOpenConns 无上限、MaxIdleConns=2、无 MaxLifetime。高并发下连接泄漏或 stale connection 风险。

**建议**: 显式配置：
```yaml
database:
  master:
    link: "..."
    maxIdle: 10
    maxOpen: 50
    maxLifetime: "30m"
```

---

### 5.4 CORS 允许所有来源

**文件**: `config/config.yaml:10`

```yaml
allowOrigins: []  # 空数组 = 允许所有
```

**问题**: 生产环境存在 CSRF 和数据泄露风险。

**建议**: 设置具体前端域名列表。

---

### 5.5 Admin 登录同时返回 User JWT

**文件**: `internal/controller/admin/admin_v1.go:59-69`

**问题**: 管理员登录时若存在对应用户，额外签发 user JWT。两个 token 使用不同 secret，管理后台持有的 user token 可能赋予超出预期的权限。

**建议**: 评估是否确实需要双 token，如不需要则移除。

---

### 5.6 MCP 缓存 TOCTOU 窗口

**文件**: `internal/logic/ai/mcp_cache.go:63-93`

**问题**: 读锁检查 → 释放 → 获取写锁之间有窗口。`now` 变量在锁外捕获，后续判断使用旧值。

**建议**: 将 `now` 获取移入写锁内，或改用 `sync.Map`。

## 六、P3 — 低优先级

### 6.1 文件上传无大小限制

**文件**: `admin_v1.go:337` — `io.ReadAll(file)` 无限制，可导致 OOM。

**建议**: 使用 `io.LimitReader(file, maxBytes)` 限制读取量。

---

### 6.2 DDL 运行时执行错误处理不完整

**文件**: `ai_chat_v1_chats.go:616-659` — 三条 DDL 语句只检查最后一条的错误，数据库可能处于部分初始化状态。

**建议**: 逐条执行并检查每条 DDL 的错误。

---

### 6.3 Input 长度与 PageSize 无上限

- `ChatReq.Message` 有 `v:"required"` 但无 max length，可提交数 MB 文本
- `AdminCaseListReq.PageSize` 默认 20 但无上限，客户端可发送 `pageSize=100000`

**建议**: 添加 `v:"max:2000"` 等验证标签。

---

### 6.4 DB debug 模式泄露连接信息

**文件**: `config/config.yaml:94` — `debug: true` 导致 GoFrame 在日志中输出连接字符串（含密码）。

**建议**: 生产环境设为 `false`。

---

### 6.5 PrivateKey 全局变量用途不明

**文件**: `internal/consts/consts.go:27` — `PrivateKey string = ""` 始终为空，用途和安全性不明。

**建议**: 确认是否仍在使用，否则删除。

---

### 6.6 Admin Like 搜索通配符未转义

**文件**: `admin_v1.go:2030-2036` — 用户输入直接拼入 `%xxx%`，若输入含 `%` 或 `_` 会操纵搜索结果。

**建议**: 转义 LIKE 通配符后再拼入。

## 七、前端专项问题

> 前端为独立 Next.js 仓库，以下为关联后端 SSE 协议的前端处理问题。

### 7.1 每帧 SSE 重建 messages 数组（性能）

**文件**: `ask-number-chat.tsx:2249-2268`

每个 `message` 事件通过 `[...prev]` 拷贝全量消息数组。高频流式会话中每秒可产生 50+ 次，导致过度渲染。

**建议**: 对最后一条消息使用 `useRef` + 周期性 `useState` 同步，或使用 `useTransition` 批量更新。

---

### 7.2 无 React Error Boundary

**文件**: `ask-number-chat.tsx`、`policy-document-chat.tsx`

ChatDbChart、Streamdown 等组件渲染异常时，整个聊天面板白屏，无恢复路径。

**建议**: 在聊天组件外层包裹 Error Boundary，捕获渲染异常后显示降级 UI 和重试按钮。

---

### 7.3 原始错误文本显示给用户（信息泄露）

**文件**: `ask-number-chat.tsx:2210`，`policy-document-chat.tsx:616`

```tsx
throw new Error(await response.text())
```

HTTP 响应体可能含内部错误详情（堆栈、数据库错误），直接显示给用户。

**建议**: 对非 200 响应返回固定错误消息，详细信息仅写 console.error。

---

### 7.4 图表类型切换状态在流式更新中丢失

**文件**: `ask-number-chat.tsx:802`

`ChatDbChart` 在每次内容变更时因 `key={index}` 重建，用户手动切换的图表类型（如从 bar → pie）在后续流式帧中被重置。

**建议**: 使用稳定的 key（如消息 ID + 图表索引），或将图表类型状态提升到父组件。

---

### 7.5 Section 解析正则过于严格

**文件**: `ask-number-chat.tsx:319`

```tsx
/^##\s*(精准结论|特征洞察|可视化|推导分析|洞察分析|结论|分析|图表)\s*$/
```

要求 `##` 后必须有空格。LLM 输出 `##精准结论`（无空格）将不被识别。

**建议**: 将 `\s+` 改为 `\s*`。

---

### 7.6 前端 API 调用无超时

**文件**: `lib/chatdb/server.ts:94-97`

对后端 `fetch` 调用无 `AbortController` 超时。若后端挂起，Next.js 服务端函数无限期阻塞。

**建议**: 添加 30s 请求超时。
